# writing-review

技術的な正しさ、文章の整合性、日本語を見るレビュー。このリポジトリの Zenn 記事・本の章向け。コードの欠陥レビュー（`/code-review`）ではない。

デフォルトは**報告のみ**。ファイルは編集しない。ユーザーが「直して」と明示したときだけ直す。

GitHub issue は作らない。このプロジェクトの `no-github-issues` に従い、指摘はチャットで終える。

## Scope

1. ユーザーが引数や `@` でパスを渡したら、それを対象にする
2. なければエディタで開いているファイル
3. それもなければ local diff（unstaged + staged）のうち `articles/` と `books/` の Markdown
4. それもなければ会話中の対象
5. 同じ本の前後の章・`overview.md`・`config.yaml` は整合性確認のために読む。無関係なファイルは触らない

## 手順

調査中は文章も変えない。公式ドキュメントが必要な主張（API、型、バージョン、関数の有無）は、学習データだけに頼らず現行 docs を当たる（Context7 があればそれを使う）。

次の 3 軸をすべて見る。軸の外のスタイル好みは書かない。

### 技術

- 型・関数・バージョン・制約が公式と一致するか
- 掲載コマンドを上からコピーして再現できるか（前提のコンテナ、ポート、待ち時間）
- 数値・次元・向き（距離は小さいほど近い／類似度は大きいほど近い、など）が実装と一致するか
- コメントとコードが食い違っていないか

### 整合性

- 冒頭の言い切りと、後半の検証結果が矛盾していないか
- 用語が揺れていないか（Community / Commercial、距離 / 類似度、など）
- 同じ現象を場所によって強く／弱く言い過ぎていないか
- ユースケースが「できること」なのか「狙うこと」なのかが読者に分かるか

### 日本語

- ですます調などの文体が揃っているか
- 言い切りが強すぎないか（0 件なのに「一部」、片方しか落ちないのに「落ちる」）
- 誤変換・誤字（文／分 など）
- コードがしていることと、地の文の主語がずれていないか

## 出力

日本語で返す。報告は次の見出しで分ける。finding には軸ごとの ID を付ける。技術は `T`、整合性は `C`、日本語は `J` で、各軸の中は 1 から連番にする（`T1`、`C1`、`J1`…）。後から「T2 を直して」と指せるようにする。

```text
### 技術

- **T1**（必須）短い指摘。該当箇所
- **T2**（任意）短い指摘。該当箇所

### 整合性

- **C1**（必須）…

### 日本語

- **J1**（任意）…
```

各 finding は短く、該当箇所（見出しや行）が分かるようにする。必須で直した方がよいものと、任意の改善を ID の直後に `（必須）` / `（任意）` で付ける。その軸に指摘が無ければ「なし」と書く。

最後に「必須で直すなら」として ID を 1〜3 点に絞る。直す許可がまだないので、勝手に編集しない。
